## 2. 先认识应用里面的分工：前端、后端、数据库与 API

先不记英文。想象你在用一个运营工作台：**上传 Excel → 看数据图表 → 请 AI 分析 → 修改日报 → 保存，明天接着用。**屏幕上的一个按钮，可能需要几个部分配合，才能真正完成这件事。

### 先记住四句话

- **前端：让你看、让你操作。**例如上传按钮、图表、日报编辑框，以及点击之后的页面变化。
- **后端：接住请求，按规则办事。**例如检查你能否读取这份资料、保存日报、代为调用模型。
- **数据库：把记录有条理地存起来，方便以后查找和修改。**例如按日期找到昨天保存的日报。
- **API：程序之间约定好的功能入口。**例如工作台按模型服务规定的格式发出分析请求，再接收结果。

### 把术语放回同一个运营例子里

| 名词 | 最简单的解释 | 在工作台里的例子／容易误解的地方 |
| --- | --- | --- |
| **前端 Frontend** | 你使用的界面，以及在用户这一侧执行的交互逻辑。 | 选择文件、切换图表、编辑正文。不是只负责“好不好看”，也可以在浏览器里读取表格、计算合计。 |
| **后端 Backend** | 接收并处理请求的服务端程序。 | 核对访问权限、保存内容、调用模型。它不是“管理员后台页面”；那个页面本身也有前端。 |
| **数据库 Database** | 可供程序保存、查询、修改记录的“电子档案柜”。 | 保存资料记录、分析结果、日报正文，再按日期或编号找回来。可以在本机，也可以在远程，不等于云端。 |
| **API（接口）** | 程序调用另一项能力时遵守的入口和规则。像办事窗口约定“交什么、返回什么”。 | 页面可以调用“保存日报”接口，后端可以调用“模型分析”接口。API 不一定属于 AI，也不一定需要走互联网。 |
| **浏览器／客户端** | 浏览器是打开网页、运行网页交互的软件；在这个例子里，它就是用户这一侧的客户端。 | 你用浏览器打开工作台。浏览器不是互联网本身，既能看本地文件，也能访问远程服务。 |
| **服务器 Server** | 响应请求、提供服务的程序；日常也用来指运行这些程序的机器。 | 你的电脑也能运行服务，所以不必先租云服务器。后端说的是程序职责，服务器说的是提供服务的一方，不是同一个概念。 |

这些是职责说明，不是要求每个应用必须买齐一套组件。概念依据：[MDN：客户端与服务端](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Server-side/First_steps/Introduction)、[数据库](https://developer.mozilla.org/en-US/docs/Glossary/Database)、[API](https://developer.mozilla.org/en-US/docs/Glossary/API)。核对日期：2026-09-23。

### 点一次“生成日报”，这些部分怎样配合？

下面是一种常见分工，用来理解概念，不是所有应用都必须照着实现：

1. **导入和查看：**你在前端选择 Excel，页面显示预览和图表。读取表格、算合计可以由普通程序完成，不必每一步都问 AI。
2. **确认和保存：**你确认资料后，前端通过接口请求后端保存。后端检查请求，把资料记录写入数据库；原始 Excel、截图等文件也可以另存在文件存储中。
3. **请求分析：**你修改分析要求并点击按钮。后端读取已确认资料，通过模型服务的 API 发送请求，收到分析结果后返回前端。**模型是这里被调用的一项能力，不是整个应用，也不等于数据库。**
4. **修改和恢复：**你在前端修改日报，保存成功后，后端把修改写入数据库。明天再打开时，程序取回已保存内容，前端重新展示。只在编辑框里出现了文字，不代表已经保存成功。

### “数据在页面上”与“数据保存了”不是一回事

- **内存／临时状态**：程序当前“手边拿着”的内容。如果没有另外保存，刷新、关闭或停止程序后就可能丢失。
- **持久化／保存**：把内容写进能保留它的存储，例如浏览器存储、本地文件或数据库，方便以后读取。原文件和提取后的记录也可以分开存。**保存不等于备份，也不等于已经同步到其他设备。**

并非所有应用都必须有独立后端和数据库：一个简单计算器可以只靠前端运行；浏览器也能保存数据。但本机浏览器里的记录，不会自动变成同事也能访问的共享资料。[MDN：浏览器端存储](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Client-side_APIs/Client-side_storage)

### 后面遇到这些词，先这样理解即可

以下是随课查阅，不要求今天背下来：

- **代码与运行**：代码是写下的操作步骤；运行是让电脑按这些步骤做事。拿到文件，不代表里面的程序已经启动。
- **HTML、CSS、JavaScript**：在网页里，分别帮助定义“有什么内容”“怎样排版显示”“怎样响应操作”。例如一个日报按钮的结构、颜色，以及点击后的动作。JavaScript 也可以用于后端，不只用来写页面。
- **运行环境与 Node.js**：程序需要合适的环境才能执行。浏览器能运行网页里的 JavaScript；Node.js 是让 JavaScript 在浏览器之外运行的一种环境，不是网页，也不是数据库。
- **依赖／库与框架**：依赖是项目需要借用的其他代码；库提供现成功能，例如读取 Excel，框架提供组织应用的基本方式。使用它们不代表业务功能会自动完成。下一节遇到的 npm 可以帮助管理依赖和运行项目脚本。

**当场自测：**“能看到昨天的日报，就证明调用了 AI 吗？”——不能，也可能只是读取保存记录。“没有独立后端，就一定不能保存吗？”——不一定，浏览器或本地文件也可以保存。“图表长得好看，就代表数据真实吗？”——不能，还要检查数据来源和计算。

**今天只要求能指出：哪里操作、谁处理请求、数据存在哪里、哪里调用了模型。**不要求写接口、设计数据库或搭服务器；Day 15 再沿真实请求详细讲数据怎么流动。接下来再看 App、PWA、HTML，才不会把“组成部分”与“产品形态”混在一起。

## 3. Application、PWA、本地 Web 应用与 HTML：概念对照表

**它们不是四种互斥的产品，更不是从低级到高级的四个阶段。** Application 是总称，Web 应用是其中一类；“本地”描述运行位置，PWA 描述 Web 应用的一组体验与能力，HTML 则是构成页面的技术。表中补充 Web 应用，是为了把这些概念连接起来。

| 概念 | 属于哪一层／一句话理解 | 通常怎样使用 | 相同点、区别与边界 | 本课程里的例子 |
| --- | --- | --- | --- | --- |
| **Application / App（应用）** | 面向用户任务的应用软件总称，不限手机软件。 | 可以是浏览器网址，也可以是手机或电脑里的应用入口。 | Web 应用、PWA、桌面和移动应用都可以属于 Application；这个词本身不说明安装方式、运行位置或是否联网。 | 能帮助运营导入资料、分析并产出日报的工具，可以叫运营应用。 |
| **Web application（Web 应用）** | 用 Web 技术提供任务和交互的软件，通过浏览器或基于 Web 的应用窗口使用。 | 打开网址；具备相应能力时，也可安装后从图标进入。 | 可以在本机或远程服务器提供服务；可以只有前端，也可以有后端。浏览器只是入口，不代表所有处理都在浏览器里完成。 | 浏览器里的运营工作台。 |
| **本地运行的 Web 应用** | Web 应用的一种运行方式：本机启动服务，再用浏览器访问。 | 先按项目说明启动，再打开 `http://localhost:端口/`；也可把启动包装成双击入口。 | 与线上 Web 应用都可以使用同样的页面技术；区别在服务运行位置。可以调用远程 AI，不能因“本地”就认定完全离线、数据不外发。 | Day 09 的工作台目前通过 `npm run dev` 启动，用 `localhost:5173` 访问。 |
| **PWA（Progressive Web App，渐进式 Web 应用）** | Web 应用的一种增强形态：在支持的环境中提供安装、独立窗口等接近普通 App 的体验。 | 可先通过网址使用，也可按浏览器／系统支持的方式安装到主屏幕或桌面。 | 本质仍是 Web 应用，不是另一种原生安装包。离线可用范围取决于实际缓存与功能设计；安装了不等于在线 AI 也能离线运行。 | Day 10 要制作、Day 13 在手机上完善的学习卡片 PWA。 |
| **HTML / `.html` 文件** | HTML 是描述网页结构的标记语言；`.html` 是常见文档后缀，不是与 App 并列的产品类型。 | 简单、独立的文件可直接用浏览器打开，也可以经 Web 服务访问。 | 单文件可同时包含 CSS 样式和 JavaScript 交互，因此不一定只是静态展示。它既可能是说明页，也可能承载轻量工具；但文件后缀不能证明已有后端、真实 AI 或 PWA 能力。 | Day 05 保留的 `index.html` 演示文件。 |

HTML 的结构、CSS 的样式与 JavaScript 的行为需要分开理解；PWA 的安装与离线能力也不能混为一谈。概念依据：[MDN：HTML](https://developer.mozilla.org/en-US/docs/Web/HTML)、[MDN：PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps)、[MDN：PWA 安装条件](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)。核对日期：2026-09-23。

### localhost、npm 与“上线”分别指什么？

- **`file:///…/index.html`**：浏览器直接读取电脑上的文件。不是所有 Web 项目都能这样打开；某些资源请求和服务端代码需要 Web 服务支持。[MDN：本地文件与本地服务器](https://developer.mozilla.org/en-US/docs/Learn_web_development/Howto/Tools_and_setup/set_up_a_local_testing_server)
- **`http://localhost:5173/`**：访问当前这台电脑上的服务；`5173` 是端口号，不是产品名字。把这个地址发给同事，对方访问的是他自己的电脑，不会自动访问你的程序。
- **npm**：JavaScript 项目常用的依赖管理和脚本运行工具；`npm run dev` 执行项目里名为 `dev` 的脚本。本项目用它启动开发预览，但并非所有 Web 应用都必须使用 npm，也不能只凭这条命令判断有没有后端。[npm：运行脚本](https://docs.npmjs.com/cli/v8/commands/npm-run-script/)
- **部署／上线**：把程序和必要服务放到目标运行环境，让目标用户能够访问。本机预览成功不等于已上线；最终用户通常不需要自己运行开发命令。

### 四个容易混淆的判断

1. **PWA 与本地运行可以重叠。** PWA 可以在 localhost 开发和调试；分发给其他设备通常使用 HTTPS。`file://` 直接打开不满足 PWA 安装要求；仅有“添加到主屏幕”入口也不证明实现了离线业务能力。[MDN：安装条件与平台差异](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)
2. **单文件不等于不能用，多文件也不等于更成熟。** 是否满足真实任务、能否正确保存和恢复、失败时能否处理，才是检查重点；运行方式不决定是不是 MVP 或正式产品。
3. **本地运行不等于所有数据都留在本机。** 调用在线模型时可能发送用户资料，必须看清实际的数据去向；即使界面已缓存，远程分析仍需要网络。
4. **Vibe Coding 是开发方式，不是产品类别。** 用它可以做 HTML Demo、Web 应用、PWA 或其他软件；也不代表做出的产品本身已接入 AI。

- [Day 09 运营工作台](<../9. llm & ai_product/amazon-ops-workbench/README.md>)：可称“通过 Vibe Coding 开发的、本地运行的 Web 应用 MVP”；目前未实现 PWA 安装与离线能力，不能直接叫 PWA。

**当场自测：**“在浏览器打开，就不是 App 吗？”“把 localhost 链接发给同事，他就能用吗？”“安装了 PWA，AI 分析就能断网使用吗？”——三题都不能这样判断。分别用应用总称、运行位置和功能依赖解释理由。

## 4. Prompt 写清六件事

Prompt 是发给 AI 的任务说明。PE 是设计并反复检查这份说明，让结果更符合任务要求；结果仍要验证。[OpenAI 官方说明](https://developers.openai.com/api/docs/guides/prompt-engineering)

> 任务目标 + 业务背景 + 输入资料 + 处理规则 + 输出格式 + 验收标准

| 部分 | 竞品追踪工作台怎样写 |
| --- | --- |
| 任务目标 | 为竞品追踪工作台搭出“样例资料 → 候选表 → 核对入表”的 Demo。 |
| 业务背景 | 日本站运营持续补入资料，需要比较同商品不同时点的数据。 |
| 输入资料 | PRD、课堂样例、已有原型；明确哪些文件能实际读取。 |
| 处理规则 | 标价与券分列；缺失不填零；观察时间不取上传时间代替。 |
| 输出格式 | 可运行代码、启动方法、已实现项与未实现项。 |
| 验收标准 | 正常资料可核对入表；缺日期时提示待补，不能补造日期；来源说明能回查。 |

**两种 Prompt 要分清：**给编程助手的 Prompt 用来搭产品；产品运行时给模型的 Prompt 用来处理用户资料。前者生成了页面，不代表后者已经接通。下面分别示范。

## 5. 课堂示范：给编程助手的 Prompt

```text
任务：
依据附件中的竞品追踪工作台 PRD 和流程简图，完成一个可运行的课堂 Demo。

背景与范围：
运营提供已有资料，产品帮助整理、核对和比较。
首版不做爬虫，不生成降价、投放或经营归因建议。
本次只用老师给的一份教学资料，跑通一条路径。

输入：
1. Day 04 的业务版 PRD
2. 教学样例、流程简图和已有代码骨架
先检查实际拿到了哪些附件；缺少影响实现的资料时说明缺项。

课堂必做：
- 资料进入候选表后，展示原文、候选值、来源位置和待核对状态。
- 标价与优惠券分列；缺失值留空并说明原因，不能按 0 计算。
- 缺观察时间可保存，但不能用上传时间代替，也不计算时间变化。
- 用户核对确认后再入表；缺项可保留，不强迫补造。
- 未接通真实解析或模型时标明“模拟提取”，说明当前实际完成的范围。

后续补齐：
修改已确认值后的关联更新、导出状态与来源说明，按 Day 06 自查逐项补。
课堂只在骨架已提供相应功能时顺带检查，不为赶进度假装已实现。

交付：
可运行代码、产物形态、启动方法、联网依赖、当前已实现项与未实现项。
说明是直接打开的 HTML，还是要先启动服务的 Web 应用；未实现 PWA 能力时不要称为 PWA。

验收：
用正常资料走通核对与入表；删除观察日期再试，检查是否正确保留缺项。
```

学员练习：把一条笼统要求改成可检查的规则。例如“错误时友好提示”改成“日期未提供时，标为待补，保留已填数据并给出补充入口”。

## 6. 复习示例：产品运行时的提取 Prompt

Day 05 老师可展示作用；Day 15 看请求链路时再解释怎样接入。以下是**已整理文字的教学样例**，不代表模型已经读取了截图或 Word。

```text
任务：从输入材料提取候选字段，供运营核对。
背景：亚马逊日本站竞品追踪。此步只整理资料，不解释经营原因。

输入材料（教学模拟，A-2 的缺失信息练习版）：
来源：A-2-缺日期，Word 段落 3（教学指定位置）
商品：竞品 A；ASIN、卖家、观察时间未提供
原文：标价 11,800 日元，展示 2,000 日元券；资格与期限未知。
说明：本练习故意移除了原案例的观察时间，用来检查缺项处理。

处理规则：
1. 只使用输入资料；身份、时间或数值缺失时标出，不推测。
2. 标价与券分开，不把减券计算写成确定成交价。
3. 保留原文与给定的来源位置，不编造定位信息。
4. 所有提取结果均为待核对候选，不自行标成“已确认”。

输出表格：
字段 | 候选值 | 单位 | 来源与位置 | 原文依据 | 缺失／待核对说明

验收：
标价为 11800，券为 2000，条件仍为未知；观察时间不补造。
输出依据和检查结果即可。
```

**看见 9,800 日元不能直接判定真实降价。** 这是券适用时的条件计算；是否适用、何时观察、与哪个旧记录比较，还需要资料与人工核对。

## 7. 电商 PE 方法速查

下表按需要查用，不是 Day 05 的必修清单。

| 方法 | 怎样用 | 容易用错的地方 |
| --- | --- | --- |
| 角色设定 Role | “协助日本站运营整理竞品记录”，说明工作视角。 | “你是专家”不能替代规则，也不证明结论专业。 |
| Zero-shot | 不给样例，先用明确要求试一次。 | 任务简单也要检查结果。 |
| One-shot / Few-shot | 给一个／少量输入输出样例，覆盖正常、缺失和边界情况。 | 样例须口径一致；这是在请求中示范，不是在训练模型。 |
| 上下文 Context | 提供商品、市场、观察时间、原始资料和已知限制。 | 资料多不等于相关；区分事实、估计和待确认项。 |
| 约束 Constraints | 写清语言、数量、不能改的事实、缺资料怎么办。 | 约束要相容且可检查；增加句子不能保证正确。 |
| 输出格式 | 人工核对用表格；程序接收可约定 JSON 字段和缺值表示。 | 格式正确不等于字段真实，见下文。 |
| 分步处理 | 把“提取 → 人工核对 → 比较”拆开，每步有可检查的输出。 | 不必让模型输出完整内部思考；要业务依据与中间产物。 |
| 多视角检查 | 分别检查运营可用性、表达和规则风险，再汇总问题。 | 同一模型换角色不等于独立专家或多个 Agent，也不是合规证明。 |
| 校验 | 对照原资料查虚构功能、漏字段、单位与引用；数值和字数可用程序核对。 | 模型自查可能重复原错误，仍需外部依据。 |
| 迭代 | 指出具体错误，一次优先改一项，再用同一组样例比较。 | 一次答对只能说明该例通过；模型或输入变化后要再检查。 |
| 资料依据 Grounding | 要求每个值或结论对应资料；资料不足就留缺项。 | 手工提供资料不等于已经搭好检索系统；RAG 在 Day 15 继续讲。 |

少量样例的作用是说明期望的判断口径与输出形式，应覆盖不同输入。[Few-shot 官方说明](https://developers.openai.com/api/docs/guides/prompt-engineering#few-shot-learning)

**JSON 约定与程序保证分开教：**在 Prompt 写“严格 JSON”只是指令。接入产品后还要解析与校验；支持结构化输出的模型可用 schema 约束结构，但内容仍可能出错。[Structured Outputs 官方说明](https://developers.openai.com/api/docs/guides/structured-outputs)

### Few-shot 怎么选例子

先定义要提取的是“材料对优惠展示的描述”，再给三个口径明确的例子：

| 输入 | 期望记录 |
| --- | --- |
| 表格没有采集券字段 | 券信息未采集；不能记为无券。 |
| 已核对截图的优惠区域未展示券 | 这份页面未展示券；不扩展为所有买家无优惠。 |
| 显示 2,000 日元券，但没有资格说明 | 券面额 2000 日元，适用条件未知。 |

若做评论分类，先定义分类对象。比如“收到时杯盖裂了”能说明破损，但不能仅凭这句话断言是物流还是质量造成的；允许“原因待确认”。

## 8. 可复用的运营 Prompt 模板

```text
任务目标：【要完成什么，交给谁使用】
业务背景：【平台、市场、商品、用户、当前阶段】
输入资料：【粘贴资料，附来源、时间及已知缺口】
处理规则：
- 【必须遵守的业务口径】
- 【不能虚构或改动的事实】
- 【资料不足、冲突或不适用时怎样输出】
参考样例：【有必要时提供输入与期望输出】
输出格式：【只保留这项任务用得上的字段或段落】
验收标准：【怎样核对准确性、完整性和格式】
```

平台字数、禁用表达和活动规则应填写本次实际依据，不把案例中的限制当成所有平台通用规则。
