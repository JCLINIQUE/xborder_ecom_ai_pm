# Day 09｜AI 分析前，资料从哪里来？

**今天学会：用一个运营日报例子，分清手动导入、Workflow、爬虫、API、MCP 和 Plugin（插件）；知道它们各做什么、怎样组合，但不会因为接上工具或装了插件，AI 就自动知道店铺的一切。**

这部分接在“模型能力与上下文”之后、“AI 产品形态对比”之前，课堂用 15 分钟认识，不要求写爬虫、配置授权或搭建自动流程。承接 [Day 05 的前后端与 API 基础](<../5. demo/Day05-PE与Demo入门.md>)，Day 15–17 再展开实现与方案取舍。

## 1. 先不讲技术：你请同事分析，也得把资料给他

你对同事说：“帮我看看昨天为什么卖得少，写一份日报。”

如果同事不知道**哪家店、哪个商品、哪一天、和哪一天比较**，也没有销售、流量或运营记录，就只能问你要资料，不能凭空知道原因。AI 也一样。

**上下文，就是 AI 这一次分析实际收到的任务背景、规则和相关资料。**不只是报表，也包括你的问题、日期范围、币种、已知事件与不能下的结论。提供上下文不等于重新训练模型。

下面是教学设想，不代表已读取真实店铺数据：

| 给 AI 什么 | 简单例子 | 为什么要给 |
| --- | --- | --- |
| 要完成的任务 | 找出需要优先核验的变化，写成可编辑的运营日报 | 明确要做什么，不让它随意发挥 |
| 范围与口径 | 日本站、商品 A、昨天与前天、日本当地日期、日元 | 避免把不同商品、时区或币种混在一起 |
| 数据和来源 | 两天的销售与流量表，标明从哪里导出、何时更新 | 有比较依据；只有昨天的数据，不能直接计算日环比 |
| 补充事实 | 运营记录写着“昨天结束优惠活动”；库存情况还没核实 | 区分已知事件与待查原因，不把猜测写成事实 |
| 输出要求 | 写“发现—依据—待核实项”，不自动修改价格或广告 | 说明结果怎么用，以及 AI 不能做什么 |

**AI 会分析，和 AI 已经拿到资料，是两件事。**模型自带的知识不能替代你昨天的私有经营数据。

## 2. 六个常见词，先分清谁负责什么

先记住最短版本：**手动＝我去拿；API＝程序调用功能的入口；爬虫＝程序去读网页；Workflow＝把几步排好；MCP＝让应用问到“有哪些工具、怎样用”，再发出调用并接收结果；Plugin＝装进或启用在某个应用里的附加功能包。**

这不是六种互斥的取数方法，更不是能力升级排名。尤其是 Plugin，它描述的是功能如何作为插件加进产品，而不是数据必定从哪里来。

| 方式／术语 | 用最简单的话解释 | 做运营日报时会怎样用 | 需要什么、有什么边界 |
| --- | --- | --- | --- |
| **手动获取，再导入** | 人先把资料找齐，再交给应用。 | 你从获授权的业务后台下载报表，把 Excel 和运营备注导入工作台；也可以上传截图、TXT、Word 或 PDF。 | 起步直观，能先确认要分析什么；但每次需要人收集、核对版本。上传还要经过读取与整理，截图不一定自动变成准确表格。 |
| **API（程序接口）** | 系统为程序提供的办事入口，规定能问什么、怎么问、返回什么。 | 假设业务系统提供了报表接口，程序带上授权和日期范围，请求昨天的销售报表。 | 要有可用接口和对应权限；只能取接口允许的数据。可能需要等待报表生成，受更新延迟、调用次数等限制。API 本身不负责每天定时运行，也不负责分析。 |
| **爬虫／网页抓取** | 让程序访问网页，再按规则找出需要的内容。本课用“爬虫”泛指这类网页采集。 | 对允许采集的教学网页，记录商品展示价格、优惠文案和观察时间，补充日报的外部参考。 | 网页价格不是店铺内部销量。页面改版、登录要求、动态内容都可能影响结果；先确认访问权限与网站规则，不绕过限制。本课程不实际新增爬虫。 |
| **Workflow（工作流）** | 事先排好“什么时候开始、先做什么、再做什么、失败怎么办”。不是一个数据源。 | 设定“每天早上 → 通过 API 取报表 → 检查日期和缺项 → 交给 AI 分析 → 保存草稿，等人审核”。也可以从你手动上传的文件开始。 | 要逐步配置输入、连接和规则。定时不代表有取数权限；其中的取数步骤仍要靠 API、文件读取或其他工具。一个工作流可以完全不使用 AI。 |
| **MCP（Model Context Protocol，模型上下文协议）** | 规定应用怎样询问工具清单、取得使用说明、发出调用并接收结果。这里先用工具调用理解它，不要求背“协议”。 | 接好之后，应用先得知“可以查销售，需要店铺和日期”，再按条件请求查询；具体三步见下一节。 | 仍要有人做好接入程序，完成连接和授权；实际查询可能依靠 API、数据库或文件。MCP 不会凭空产生数据，也不只支持工具，还可提供资料和提示模板。 |
| **Plugin（插件）** | 给现有应用增加能力的组件或功能包，通常通过安装或启用来使用。 | 假设启用“经营数据插件”，应用增加销售查询和日报模板；查询能力还需要连接相应数据来源。 | 插件可能直接调用 API，也可能包含 MCP 配置，或只提供本地功能。不同产品的插件不一定通用；安装、连接、授权是不同状态。 |

概念参考：[MDN：API](https://developer.mozilla.org/en-US/docs/Glossary/API)、[MDN：Crawler](https://developer.mozilla.org/en-US/docs/Glossary/Crawler)、[n8n：工作流](https://docs.n8n.io/workflows/)、[MCP 官方入门](https://modelcontextprotocol.io/docs/getting-started/intro)。核对日期：2026-09-23。表中运营流程是教学设计，不是任何产品已经接通亚马逊渠道的承诺。

## 3. 重点辨析：用一次查销售，看懂 API、MCP 与 Plugin

先不背“共同连接规则”。假设你说：**“查 A 店昨天的销售额。”**下面的工具、店铺和结果都只是教学设想，不表示已经接入真实账户。

### 3.1 API：销售系统实际提供的查询入口

假设销售系统有一个功能：**程序提供店铺和日期，它就返回销售记录。**这个供程序调用的入口，就是一个业务 API；开发者要知道它的具体用法，完成接入和授权。

只有你说的那句话还不够，应用仍要确定“昨天”是哪一天、哪个时区，以及 A 店对应哪个账户，再把条件交给程序查询。API 不会自动理解所有人话。[API 的含义](https://developer.mozilla.org/en-US/docs/Glossary/API)

### 3.2 MCP：把程序之间传的消息，翻译成三步问答

假设开发者已经做好一个“销售查询接入程序”，它背后能调用上面的销售 API。AI 应用连上它后，会有类似下面的消息往来：

| 步骤 | AI 应用发什么 | 接入程序回什么 |
| --- | --- | --- |
| **① 问有哪些工具、怎样用** | “列出你能提供的工具。” | “我有一个‘查询销售’工具。用途是读取销售额，必须提供店铺和日期。” |
| **② 指定工具，填好条件** | “调用‘查询销售’，店铺=A，日期=已确认的昨天日期。” | 接入程序核对条件与权限，然后调用销售系统查询。 |
| **③ 接收结果或错误** | 应用等待这次调用的结果。 | 返回销售额、币种和日期等结果；如果没有权限或查询失败，就返回相应错误，而不是编造金额。 |

**MCP 规定的就是这类消息怎样组织和传递**：怎么列工具、怎么描述必填条件、怎么指定工具调用、怎么返回结果。上表是白话翻译；实际传的是程序能读取的消息，不是在后台有人聊天。[MCP 官方：工具清单与调用](https://modelcontextprotocol.io/docs/learn/server-concepts)

换成库存工具，第一步可能回答“我能查库存，需要商品编号”；**工具名称和条件不同，但兼容的应用可以用同样的方式问清单、发调用、读结果。**这才是“共同”的具体含义，不是所有数据都变成同样的字段。

**工具本身仍要有人实现。**MCP 不是自动制造工具的 AI，也不会自动连接全网；应用还要支持它，接好相应程序并完成授权。模型可以根据工具说明提出调用请求，执行和权限检查仍由程序负责。这里用工具调用说明 MCP；它也支持提供资料和提示模板，不限于这三步。[MCP：接入程序与能力](https://modelcontextprotocol.io/docs/learn/architecture)

### 3.3 不用 MCP，API 能不能给 AI 用？能

| 同一个查询任务 | 经过什么 | 关键区别 |
| --- | --- | --- |
| **直接接 API** | AI 应用 → 写好的接入代码 → 销售 API | 开发者按这个 API 的用法接进应用；也可以把查询工具提供给模型选择。 |
| **通过 MCP 接入** | AI 应用 → MCP 接入程序 → 同一个销售 API | 接入程序按上述“列工具、填条件、发调用、读结果”的方式提供能力，兼容的应用可以复用；业务 API 的对接仍要做好。 |

两条路线都能支持“用一句话查销售”，都不会自动获得权限。普通 API 也可以有机器可读的说明，不能说只有 MCP 才能描述工具。**API 是接口的大类概念，MCP 是具体协议；这不是“API 给人用、MCP 给 AI 用”的区别。**

MCP 接入程序也可以直接读取文件或数据库，不一定绕过一个外部 API。只有固定查询需求时，直接接 API 可能已足够；已有合适的 MCP 工具，或需要多个兼容应用复用时，再考虑 MCP，不按技术名字排等级。

### 3.4 Plugin：你给某个应用安装或启用的“附加功能包”

想象一个原本没有销售查询功能的 AI 应用。开发者做了一个**“经营数据插件”**，你在支持它的应用里安装或启用；它可能带来“查销售、查库存”的工具，以及一份日报模板。

**Plugin 说的是这些能力怎样作为一个插件加进产品，而不是它们怎样取数据。**这个假设插件内部可以直接调用 API，也可以带上 MCP 接入配置；另一种“日报模板插件”可能只带模板，根本不取外部数据。

不同产品对 Plugin 的打包内容、安装方式和权限要求不同，不能默认跨产品通用。例如 Claude Code 的插件可以包含指令类能力和 MCP 接入配置；这只是一个具体产品的例子，不是所有插件的定义。[Claude Code：插件包含什么](https://code.claude.com/docs/en/plugins) · [WordPress：用插件扩展功能](https://developer.wordpress.org/plugins/intro/)

### 3.5 三个词放到一起记

| 名词 | 在这个例子里是什么 | 不要误认为 |
| --- | --- | --- |
| **API** | 销售系统提供给程序的查询入口 | 已经做好的整个插件，或自动理解人话的模型 |
| **MCP** | 让应用按规定的消息格式问工具清单、填条件调用、接收结果的协议 | 销售数据本身，或装上就会自动查所有账户的工具 |
| **Plugin** | 安装／启用到某个应用里的附加功能包，里面可以带查询工具、模板等 | 一定使用 MCP，或一定能联网取数 |

同一个功能里可以同时出现三者：**你启用经营数据插件 → 插件带来 MCP 接入配置 → 应用按 MCP 方式调用查询工具 → 工具调用销售 API。**这只是可能的实现，也可以跳过 MCP 直接用 API；MCP 接入也不一定要通过插件安装。

**安装、连接、授权要分别确认。**看到插件已安装，不代表外部服务已连上，更不代表它有权读取你的店铺。还要看清实际启用了哪些工具、能访问哪些资料、数据是否会发送给外部服务。课堂只理解，不安装插件。

## 4. 它们为什么能组合？

### 例子 A：第一版先手动

你下载 Excel，补一段“昨天结束活动”的文字，导入工作台并核对。应用把相关数据与要求交给模型，返回分析，再由你修改日报。

**这里有 AI 分析，但不必有 MCP、爬虫或自动取数。**如果文件内容不可靠，加上自动化也不会让它自动变准确。

### 例子 B：每天重复的事，用工作流安排

工作流到点启动，调用业务 API 取数据；检查日期、币种和必需字段，合格后再生成日报草稿。不合格则保留缺项并提示运营处理，不能拿旧报表冒充今天的数据。

**Workflow 管步骤，API 管调用入口。**“每天自动拿资料”通常是多种能力配合，不是 Workflow 自己拥有资料。[n8n：定时触发](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.scheduletrigger/)

### 例子 C：临时追问，通过 MCP 接好的工具查

你临时问“再看看这个商品上周的情况”。支持 MCP 的 AI 应用可以通过接好的只读查询工具请求数据；该工具背后可能继续调用同一个业务 API。

这里就是第 3 节的步骤：应用问到“有什么工具、需要什么条件”，再请求工具查询。接入程序也可以只读取一个已授权的本地文件夹，不一定调用外部 API。具体由谁发起调用、是否需要确认，仍由应用设计与权限控制决定。[MCP：架构与工具／资料](https://modelcontextprotocol.io/docs/learn/architecture)

### 例子 D：网页信息是另一种来源

内部报表回答“自己卖了多少”，经允许采集的网页可补充“对方当时展示了什么价格”。即使工作流同时收集了两者，也必须保留来源、采集时间和不同口径；不能把网页展示价格直接当成成交价，更不能据此推算竞品真实订单量。

“Connector／连接器”也常出现在产品里，可先理解成“已经做好的某个系统的接入模块”。它可能使用 API 或 MCP 等方式；看到这个名字，仍要问：**究竟连哪个系统、可以读什么、是否还需要授权？**

## 5. 拿到文件，不等于已经成为好用的上下文

前面介绍了资料怎么来、工具怎么调用，以及插件怎样增加功能。即使这些已经接好，随后还需要：

1. **读出来：**Excel 要识别表头；截图可能要 OCR（把图里的文字识别出来）；Word、PDF 要提取内容。格式能打开，不代表数字识别正确。
2. **核对好：**确认日期、单位、重复行、空值、来源与更新状态。不同渠道的数据不能不加检查就相加。
3. **挑相关的：**围绕这次问题选择必要行、摘要和备注。模型一次能接收的内容有限，导入的大文件可能只发送了部分内容，要告诉用户范围和缺项。
4. **交给模型：**应用把选好的资料和任务要求加入这次请求。工具返回结果后，也通常由应用组织进模型输入；不是模型自己越过授权去读取账户。

**文件已经上传、渠道已经连接、资料已经保存、模型本次实际读到什么，是四种不同状态。**报告中应能查到依据；没取到的数据要标记缺失，不靠编造补全。

安全边界也要看清：只取任务需要的数据，优先只读授权；说明哪些资料将发送给外部模型。读取报告的权限，不等于允许改价、调广告或发消息。网页和文档里的文字是待分析资料，不应自动变成应用要执行的指令。

## 6. 初学者怎样为当前 MVP 选方式？

| 眼前的问题 | 可以先考虑什么 | 先问的一句话 |
| --- | --- | --- |
| 还没搞清要分析哪些表，先验证日报是否有用 | 手动导入真实样例 | “这些资料足够支持要回答的问题吗？” |
| 数据需求固定，系统提供可用接口，天天重复收集 | API 取数，按需用 Workflow 安排执行 | “有权限吗？数据何时更新？失败时怎么办？” |
| 希望在支持的 AI 应用中随问随查外部资料 | 评估现成或可开发的 MCP／连接器 | “实际能读哪些内容？接入和权限是否已经就绪？” |
| 想从网页补充信息，但没有合适接口 | 先核对授权、网站规则和采集可行性，再评估网页采集 | “有权访问和采集吗？页面上的值究竟代表什么？” |

**当前工作台仍以手动导入为主。**学习这些概念不代表本轮要新增自动取数、MCP 或爬虫功能；不要把未接通的渠道展示成可用功能。先把“真实资料 → 核对 → 分析 → 可修改日报”做好，再按业务需要接数据。

这里还要分别回答三个问题：**数据从哪来？谁安排执行？用户怎样与结果协作？**它们对应不同设计决定；换成聊天界面不会自动接通数据，接上 MCP 也不等于产品更 AI-native。

## 7. 15 分钟讲练与学习卡

- **3 分钟：**用“同事没资料就无法分析”的例子，补齐任务、范围、数据和来源。
- **3 分钟：**看六个词的对照表，区分取数、安排步骤和插件增加功能。
- **5 分钟：**用“查昨天销售额”的三步问答看懂 MCP，再与 API、Plugin 对照；不从抽象的“共同规则”开始讲。
- **2 分钟：**学员为同一个日报任务选第一版取数方式，说明理由与一个风险。
- **2 分钟：**回答下方自测，并把判断记进原有的 3–5 张学习卡，不另交接入项目。

| 自测题 | 参考回答 |
| --- | --- |
| “我写了每天 9 点运行，AI 就能取到店铺数据了吗？” | 不能。还要配置实际来源、取数工具、权限与失败处理。 |
| “MCP 比 API 高级，所以有 MCP 就不需要 API？” | 不是升级替代关系。MCP 接入的工具背后仍可能调用业务 API。 |
| “API 给普通程序用，MCP 才能让 AI 查数据？” | 不对。AI 应用也能直接集成业务 API；两种方式都由程序实际执行调用。 |
| “MCP 的共同规则，具体共同在哪？” | 应用用约定的消息格式问有哪些工具、取得必填条件、发起调用并接收结果；各个工具仍可有不同名称和条件。 |
| “已经有销售 API，为什么还可能做 MCP 接入？” | 让兼容的应用用上述方式调用同一组工具，方便复用；实际查询仍依靠接好的业务能力。 |
| “Plugin 就是 MCP 吗？” | 不是。Plugin 是加进某个应用的功能包，可能带 MCP 配置，也可能直接调用 API，或只提供本地功能。 |
| “插件已安装，就能读取我的店铺了吗？” | 不一定。还要确认是否启用、服务是否连上，以及是否有相应账户的数据权限。 |
| “网页抓到一个价格，就知道对方昨天成交了多少？” | 不知道。展示信息不能替代内部成交数据。 |
| “Excel 已经上传，所以 AI 一定看过全部内容？” | 不一定。要检查解析、筛选与本次实际发送范围。 |
| “没有自动取数，手动导入的工作台就不算 AI 产品？” | 不是。数据获取方式与是否使用 AI 能力是不同问题。 |

**学习卡示例：装一个经营数据插件时，Plugin、MCP、API 各做什么？**用“查昨天销售额”解释，不只重复术语；附来源、核对日期、自测题和解析。仍只交同一组 3–5 张卡：至少一张产品形态对比、一张数据获取与接入对比，另用卡片覆盖模型基础；Day 10 沿用这些卡片做学习 PWA。
